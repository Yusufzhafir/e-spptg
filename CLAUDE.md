# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

E-SPPTG is a digital land-registration system for Indonesian local government: officials process citizen land claims (pengajuan) through a multi-step workflow, validate boundaries against prohibited areas with PostGIS, and issue official SPPTG certificates as PDFs. UI text and domain vocabulary are Indonesian — see the glossary in AGENTS.md, which also documents known bugs, incomplete features, and detailed endpoint/schema tables.

## Commands

Use **pnpm** (lockfile is `pnpm-lock.yaml`).

```bash
pnpm dev                # Next.js dev server (http://localhost:3000)
pnpm build              # Production build (also serves as the type check)
pnpm lint               # ESLint (eslint-config-next + unused-imports)
pnpm test               # All unit tests (Vitest, node environment)
pnpm vitest run src/lib/kmz-parser.test.ts   # Single test file
```

Vitest only picks up `src/**/*.test.ts`; tests are colocated with the code (mostly pure-logic modules in `src/lib/` and `src/server/s3/`). Vitest globals are enabled — no `describe`/`it`/`expect` imports needed.

Database (Drizzle Kit, per-environment configs):

```bash
pnpm generate:stag / generate:prod   # Generate migrations into drizzle-stag/ or drizzle-prod/
pnpm migrate:stag / migrate:prod     # Run migrations (preferred over push for existing envs)
pnpm push:stag / push:prod           # Push schema directly (can fail on PostGIS typmod conflicts)
```

## Environment & infrastructure

- The env file is `.env.development.local` (gitignored via `.env*`) — loaded automatically by Next.js and explicitly by `stag.drizzle.config.ts`; `prod.drizzle.config.ts` loads `.env.development.prod`. There is no committed template; required keys are listed in AGENTS.md under "Environment Variables".
- **Database is PlanetScale Postgres** (`*.pg.psdb.cloud`, region ap-southeast-2/Sydney) with PostGIS 3.5. Two URLs to the same database: `DATABASE_URL` (port 6432, connection pooler — app runtime via `src/server/db/db.ts`) and `DATABASE_URL_DDL` (port 5432, direct connection — drizzle-kit only; DDL must not go through the pooler). Drizzle configs fail fast if `DATABASE_URL_DDL` is missing.
- **Object storage is Biznet NEO** (`nos.jkt-1.neo.id`, Jakarta), S3-compatible. The `AWS_*` env vars are NEO credentials, not real AWS — the name comes from `@aws-sdk/client-s3`.
- `import 'dotenv/config'` in `db.ts` reads `.env` (which doesn't exist), so code touching the DB outside Next.js (Vitest, standalone scripts) must inject env manually, e.g. `dotenv.config({ path: '.env.development.local' })`.

## Application flow

1. **Login & registration**: Authentication is the app's own — email + scrypt password hash, server-side `sessions` rows keyed by the SHA-256 of an HttpOnly cookie (`src/server/auth/`). `src/proxy.ts` gates `/app/*` on cookie presence only (Edge, no DB); `/api/trpc` stays open so login/register/reset are reachable. Self-registration always creates a `Viewer`; admins create accounts from Pengaturan, which always mails an invite link (there is no initial-password option) — opening it sets the first password and verifies the address in one step. Roles (`peran`) — five of them: `Superadmin` (everything), `Admin`/`Verifikator` (scoped to their `assigned_village_id`), `Kecamatan` (**read-only** oversight of every desa in its `assigned_kecamatan`; takes no part in the workflow — no drafts, no comments, no status or validity changes), `Viewer` (own drafts only, Step 1 only).
2. **4-step submission wizard** (`src/components/SubmissionFlow.tsx` + `submission-steps/Step1…Step4`). In-progress data lives as JSONB in `submission_drafts.payload`, validated per step by Zod schemas in `src/lib/validation/submission-draft.ts`, saved via `drafts.saveStep`:
   - **Step 1 — Berkas**: pick desa, applicant data (nama, NIK, alamat), upload mandatory KTP + KK plus supporting documents.
   - **Step 2 — Lapangan**: land boundary coordinates (geografis/UTM, map polygon drawing, or KML/KMZ import), area, boundary witnesses (saksi), survey team (juru ukur). A pengajuan may cover **several bidang** — `payload.polygons` is the list, and `coordinatesGeografis` is a mirror of its first entry kept for pre-multi-polygon drafts. **At most `MAX_POLYGONS_PER_SUBMISSION` (2)**, an office rule rather than a technical one: more separated parcels than that are filed as more than one pengajuan. Enforced in the editor (the add button disables, an import of more bidang is refused rather than truncated — a certificate quietly missing a parcel is worse than an error) and again by `landPolygonSchema`'s list bounds. Always write both through `polygonsPatch` (`src/lib/land-polygons.ts`); a KML import loads every polygon in the file and marks each `locked` so the stored boundary cannot drift from the survey file. **Nomor persil, luas manual, panjang and lebar belong to a bidang, not to the pengajuan** — a claim of three parcels has three of each, and folding them into one value said something false about all but one. The draft-level keys of those names still exist as derived mirrors (luas manual is the **sum**, the other three mirror the first bidang) so `submissions.luas_manual` and pre-move payload readers keep working; `derivedBidangFields` writes them, and `draftPolygons` adopts a pre-move draft's values onto its bidang — but **only when there is exactly one**, since on a berkas that already covered several the old value described all of them at once.
   - **Step 3 — Hasil**: PostGIS overlap check against `prohibited_areas`, then the verifier picks a status decision (see lifecycle below).
   - **Step 4 — Terbitkan SPPTG**: enter the certificate number, render the 4-page SPPTG PDF (react-pdf, `src/components/pdf/`), upload it to S3 as a `SPPG`-category document. Reachable from **two** decisions, and which one changes the whole stage — see "Two certificates" below.
3. **Editing a filed pengajuan**: editing is always **in place** — the table's Edit action is a plain confirmation, and `drafts.createFromSubmission` always sets `editing_submission_id`, so re-filing updates the same row. Opening the editor flags that submission `is_valid = false` immediately (the version on the map is now known to be superseded); `submitDraft` sets it back to valid when the corrected berkas is filed, and an abandoned draft leaves it invalid until someone flips it back from the detail page. Separately, and not to be confused with it, `checkOverlapsFromCoordinates` takes the `draftId` and **excludes the pengajuan that draft is editing** (`submission_drafts.editing_submission_id`), resolved server-side — a boundary cannot overlap itself, and a caller-supplied id would let anyone hide a pengajuan from their own check. That exclusion is what makes the overlap check correct regardless of the validity flag.
4. **Final submit**: `submissions.submitDraft` converts the draft into a permanent `submissions` row — `owner_user_id` (draft creator), `verifikator` (processor), `geom` (PostGIS **MultiPolygon**, SRID 4326, one part per bidang), and the Step 3 status (default `'SPPTG terdata'`).
5. **Post-submit**: dashboard (per-status KPIs, filters, map). Status can still change via `submissions.updateStatus` (verifikator+); every change is recorded in `status_history` / `riwayat` as an audit trail.

## SPPTG status lifecycle (`status_spptg` enum)

| Status | Meaning | Rules in code |
|---|---|---|
| `SPPTG terdata` | Recorded, **no approval** — the initial/default status; may still be issued its own certificate | Applied by `submitDraft` when the draft has no valid status. Reaches Step 4 and issues the *terdata* certificate |
| `SPPTG terdaftar` | **Approved** — passed verification, officially registered; prerequisite for Step 4 issuance | Choosing it when PostGIS found overlaps triggers a confirmation warning (`Step3Results.tsx`) |
| `SPPTG ditinjau ulang` | **Needs revision** — returned to applicant | Feedback/reason **required**; may attach `Lampiran Feedback` documents |
| `SPPTG ditolak` | **Rejected** permanently | Feedback/reason **required** |
| `Terbit SPPTG` | Certificate **issued** — intended final state | ⚠️ **Never actually set by any code path**: `submitDraft` whitelists only the other four statuses, Step 4 generates the PDF without changing status, and `StatusBadge.tsx` excludes it from its config. "Issued" is currently only observable via the certificate number + uploaded `SPPG` PDF document |

`terdata` vs `terdaftar` is the confusing pair: `terdata` = "in the system, awaiting decision"; `terdaftar` = "approved".

## Architecture

**Stack**: Next.js 16 App Router, React 19, tRPC v11, Drizzle ORM on PostgreSQL + PostGIS, self-hosted auth (scrypt + DB sessions), Tailwind 4 + shadcn/ui, S3-compatible storage, Google Maps (`@vis.gl/react-google-maps`), `@react-pdf/renderer` for certificates, nodemailer over Gmail SMTP for password-reset mail, Zod v4.

**Request path**: `src/proxy.ts` (Edge session-cookie gate) → tRPC handler at `src/app/api/trpc/[trpc]/route.ts` → routers in `src/trpc/routers/` (auth, drafts, documents, submissions, prohibitedAreas, villages, users) → query functions in `src/server/db/queries/`. The single Drizzle schema is `src/server/db/schema.ts`.

**Statistics API** (`/api/statistik`, `src/app/api/statistik/` + `src/server/public-api/`) is the one route family outside tRPC: read-only aggregate JSON for the Dashboard Eksekutif Kutai Timur. It authenticates on `X-Client-Id` / `X-API-Key` pairs from `STATISTIK_API_CLIENTS` (not sessions, not the DB), optionally restricts callers to `STATISTIK_API_ALLOWED_IPS`, and returns `503` when neither is configured — so it is off by default. It sends no CORS headers on purpose (server-to-server only) and must never expose applicant fields; see `docs/API-STATISTIK.md`.

**Public/SEO surface**: the landing page `/` is the *only* indexable route, and it is a **server component on purpose** — it renders `<LandingPage />` unconditionally so the prerendered HTML carries the real copy (`RedirectSignedInHome` is a null-rendering client safety net; `src/proxy.ts` already redirects signed-in visitors server-side). `src/lib/site.ts` holds the canonical origin and the private-path list that `robots.ts` and the per-page `noindex` both read; `sitemap.ts` and `opengraph-image.tsx` (generated card, no external assets) sit beside them. `/app/*` and `/api/*` also carry `X-Robots-Tag: noindex` from `next.config.ts`. If you make `/` client-gated again, the page silently drops out of search results — verify with `grep '<h1' .next/server/app/index.html` after a build. The page is prerendered with `export const revalidate` (ISR) rather than statically forever, because its **"Data Statistik" section is real data**: `src/server/landing-stats.ts` reads it server-side (through the same `dash:` Redis prefix `invalidateDashboard()` already clears) and hands it to `<LandingPage stats>`. Two rules there. It counts **only `SPPTG terdaftar` and only `is_valid` rows** — publishing per-desa counts of rejected or still-undecided berkas says something about people the office has not finished deciding about. And the query behind it (`getRegisteredStatsByVillage`) selects **counts and summed `luas` only**, never a nama/NIK/alamat/geometry column, so an anonymous visitor cannot be shown an applicant even by an accidental join; keep it that way rather than reusing a scoped dashboard query here. A failed read returns `null` and the section renders an empty state — the public page of a government service must not 500 because Postgres blinked.

The landing page carries **three public data blocks**, and what makes each one safe is different:
1. **Data Statistik** — the aggregates above, prerendered with the page.
2. **Sebaran bidang** (`PetaSebaranSection`, Google Maps) — outlines and nothing else. `getRegisteredPolygons` selects *one* column, the simplified geometry, so there is no id to join back on and no popup to open; the camera ignores points outside a Kalimantan bounding box, because a single mis-digitised boundary otherwise `fitBounds`-es the public map out to a view of the planet. The Maps JS loads only when the section nears the viewport — every load is billable and this page is open to bots.
3. **Statistik Kunjungan** (`page_visits` + `POST /api/kunjungan` + `kunjungan.statistik`) — the visit counter. It is a **beacon**, not a server render, precisely because the page is ISR'd; it refuses bots (`src/lib/user-agent.ts`), refuses any path under `PRIVATE_PATH_PREFIXES`, and is rate-limited per IP. Read back client-side, never baked into the HTML: "aktif 5 menit terakhir" frozen for fifteen minutes would be a lie. `page_visits.ip` holds the **raw address** (an explicit operator decision) which makes it the only table here holding personal data about people who never signed in — so the read path exposes it only inside `COUNT(DISTINCT ip)`, and `hapusKunjunganLama` prunes past `VISIT_RETENTION_DAYS`. `negara`/`kota` come from proxy headers (`CF-IPCountry`, `X-Geo-*`) and stay empty otherwise; the app makes no outbound geolocation call. Timezone-bucketed aggregates inline `'Asia/Makassar'` with `sql.raw` on purpose — a bound parameter makes Postgres reject the `GROUP BY` because it cannot prove `$1` and `$4` are the same expression.

Charts on this page are **Recharts** (`KecamatanCharts`, `TrenKunjunganChart`) — the same library the in-app dashboard uses, so there is no second charting bundle. It replaced amCharts, which was removed for one reason worth keeping in mind before reaching for another chart library here: **its free licence requires its branding logo to stay on the chart**, and a vendor mark on a kabupaten's public portal is not acceptable. The figures are always printed as text beside the chart as well — an SVG of bars gives a crawler and a screen reader nothing.

The **per-desa table** (`TabelPerDesa`) filters by year in the browser: `getRegisteredStatsByVillage` groups per desa *per year*, so `rekapDesa()` can fold the rows for any year without a round trip that would make a prerendered page dynamic. Its "Export ke Excel" writes a real `.xlsx` through `src/lib/xlsx-export.ts` — a zip of four small XML parts built with the JSZip already here for KMZ, rather than a megabyte of SheetJS for one button — and both the table and the file come from the same `rekapDesa()` call, so a download can never disagree with the figures on screen.

**Audit trail** (`src/server/audit/` + `audit_logs` table, UI at Pengaturan → Audit Log). A middleware on `protectedProcedure` records **every authenticated mutation** — succeeded or failed — keyed by the tRPC procedure path, so a new mutation is audited without registering it anywhere. A procedure adds a before/after snapshot by calling `ctx.audit.set({ sebelum, sesudah, ringkasan, entitasId })`; without it the entry still lands, just with the (redacted) input instead. `redact()` strips anything whose key looks like a password/token/hash before it is stored — never bypass it by writing to `audit_logs` directly. Public auth procedures (login, register) sit below the middleware and call `recordAudit()` themselves; failed logins are recorded nowhere else. Every `audit.*` procedure is `superadminProcedure`, and deleting an entry is itself audited with the deleted entry's contents in the summary.

**Redis** (`src/server/redis/`) backs sessions, rate limiting and read caching. Every use goes through `withRedis()`, which returns a fallback when Redis is unreachable — so a cache outage degrades the app (slower, more Postgres reads) instead of breaking it, and `REDIS_URL` being unset is a supported local-dev configuration. Two rules when adding to it: **the user row is never cached without explicit invalidation** (`src/server/db/queries/user.ts` invalidates inside every write function, because `validateSessionToken` reads the user through that cache on every request — a miss means stale permissions), and **anything scoped per role uses `scopedKey()`**, which hashes the scope into the key so one role's dashboard numbers cannot be served to another. Sessions are written to both Redis and Postgres: Redis serves every request, Postgres is the durable copy that survives a Redis restart and still powers "perangkat aktif".

**Authentication** lives in `src/server/auth/`: `password.ts` (scrypt hash/verify), `session.ts` (create/validate/revoke, 30-day sliding expiry), `cookies.ts` (`espptg_session`, HttpOnly/Lax/Secure), `password-reset.ts` (single-use 1-hour tokens), `mailer.ts` (Gmail SMTP — the only third-party call left), `rate-limit.ts`. Only token *digests* reach the database. `users.password_hash` must never leave the server: every read procedure passes rows through `toClientUser`, which swaps it for a `hasPassword` boolean.

**SSO Kutai Timur** (`src/server/auth/sso.ts` + `src/lib/sso-config.ts`) is an **optional second door**, off unless `SSO_ENABLED` is on and fully configured — anything missing logs an error and falls back to off, and every SSO route then answers 404. It never replaces the password form: with SSO on, every account (gmail included) still signs in exactly as before, and the SSO button only adds Keycloak (realm `kutimkab`) for addresses in `SSO_ALLOWED_EMAIL_DOMAINS`, default `kutaitimurkab.go.id`. Three rules. **`users.sso_sub` is the identifier, never the email** — it is a Keycloak UUID that survives an admin editing someone's address, and email is used exactly once, to *offer* linking an SSO identity to an account that already exists (`/sso/hubungkan`; linking silently would hand anyone who can authenticate as that address whatever the local account can do). **An SSO first login always creates a `Viewer`**, same as self-registration — the `roles` claim describes the realm, not this app, and honouring it would let the IdP mint a Superadmin here. And **no ID-token signature check is needed in this flow and none is done**: tokens arrive as the body of our own TLS call to the token endpoint and the identity is read back from `userinfo`, so nothing here ever trusts a token somebody handed us — an API that *accepts* SSO bearer tokens would be a different problem needing JWKS. The handshake state and the pending link ride in HMAC-signed HttpOnly cookies, which is what makes login CSRF and account-takeover-by-cookie-planting fail. `/callbacksso` is at the top level, not under `/api`, because that exact path is what Diskominfo registered.

**Authorization is two-layered**:
1. Procedure middleware in `src/trpc/init.ts`: `publicProcedure` → `protectedProcedure` → `verifikatorProcedure` (Superadmin/Admin/Verifikator) → `adminProcedure` (Superadmin/Admin) → `superadminProcedure`. The role field is `appUser.peran`. `Kecamatan` clears only `protectedProcedure` — it is deliberately absent from every tier above, which is what makes it read-only.
2. Row-level scoping via `src/server/authz.ts` — reuse these helpers (`canAccessDraft`, `assertCanAccessSubmission`, `getSubmissionScopeForUser`, …) in routers rather than reimplementing checks. `submissions.owner_user_id` is the source of truth for Viewer visibility; `verifikator` is the processor, not the owner.
3. Document-category scoping, also in `authz.ts`: the oversight roles (`Superadmin`, `Kecamatan`) see **only the `SPPG` category** on a filed pengajuan — never the KTP, KK or any other berkas. Enforced server-side in `documentRouter` (`listBySubmission` filters, `getSignedDownloadUrl`/`getById` refuse) via `canViewSubmissionDocumentCategory`; `DetailPage` mirrors it so the UI explains the gap. Drafts are deliberately exempt — the wizard has to render its own uploads, and `Kecamatan` cannot reach a draft anyway.

Two submission-flow gotchas that have caused real data loss:
- On step transitions, the current step's data must be **explicitly saved before** updating `currentStep` — do not rely on auto-save intervals or unmount effects (race conditions).
- The payload passed to `saveDraftStep` is manually constructed; a field missing there silently never persists, even though local state looks correct.

**Notifications** are two layers over one event. The durable layer is the `notifications` table written by `createNotification` — read back scoped-by-role in `listNotificationsScoped` and polled every 30s by `NotificationBell`. On top of it, **Web Push** (`src/server/push/`) delivers the same event to the browser and the installed PWA: `push_subscriptions` holds one row per browser endpoint, `webpush.ts` signs with VAPID (`VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`), and `public/sw.js` renders the notification. Three rules: push follows the `withRedis()` pattern — **unset VAPID keys are a supported configuration**, the whole thing no-ops and the bell still works; `pushSubmissionEvent` is called **after the transaction commits**, never inside it, so a rollback cannot notify people about a pengajuan that does not exist; and `listNotificationRecipientUserIds` must keep mirroring `listNotificationsScoped`, or someone gets pushed a pengajuan they cannot open. Events wired up today: `submissions.submitDraft` (created/updated) and `submissions.updateStatus` (status).

**Spatial analysis**: `src/server/postgis.ts` runs raw PostGIS queries (`ST_Intersects`/`ST_Intersection`/`ST_Area`) to check submission polygons against `prohibited_areas.geom` (protected zones: Kawasan Hutan, Tanah Pemerintah, Sempadan Sungai, … — the 14 values live in `src/lib/prohibited-area-types.ts`, the single source for the pgEnum, the TS union, the Zod schema and every dropdown); results are cached in `overlap_results`. Coordinate/GeoJSON/UTM helpers live in `src/lib/` (`map-utils.ts`, `utm-conversion.ts`, `land-polygons.ts`), with KMZ/KML **import** in `kmz-parser.ts` and the matching **export** (detail page → "Unduh Peta Lahan") in `kml-export.ts`. `parseGeospatialFile` is the one entry point every importer calls: it routes on extension, and a `.zip` goes to `shapefile-parser.ts` — an ESRI shapefile set (.shp/.dbf/.shx/.prj/.cpg), which is how ArcGIS and QGIS hand a boundary over, read through shpjs (lazily imported: it drags in proj4 and a DBF reader). Two rules there. **The `.prj` is what makes a shapefile safe**: survey data here arrives in UTM 50N metres, shpjs reprojects to WGS84 only when the `.prj` is present, and a file that comes through still projected is refused by an explicit degrees check — read as degrees, an easting of 500 000 puts a parcel in the Gulf of Guinea rather than Sangatta. And a `.zip` with no `.shp` falls back to being read as a KMZ, because that is nearly always what it is. `parseKMLPolygons` returns **every** polygon in a file, and both geometry columns are `geometry(MultiPolygon,4326)`: the wizard turns a file's polygons into the pengajuan's bidang (at most `MAX_POLYGONS_PER_SUBMISSION`) and the kawasan form turns them into the blocks of one kawasan. **The two callers have different ceilings, and only the wizard has any.** A bidang lives as JSON in `submission_drafts.payload` where `landPolygonSchema` caps it at `DEFAULT_MAX_POLYGON_POINTS` (100) vertices, so an import over that has to fail at import time rather than later on save; a kawasan has no count limit at all — any number of blocks, each of any number of vertices, because the geometry goes straight into PostGIS and a Kawasan Hutan traced from an SK is routinely thousands of points. `KawasanGeometryEditor` therefore passes `maxPoints: UNLIMITED_POLYGON_POINTS`; do not "tidy" that back to the default. The bulk importer on Pengaturan → Kawasan is "Impor Massal" (`prohibitedAreas.createBulk`) — see below. **An imported polygon arrives `locked`** — the file is the authority for where a boundary runs, so its vertices are frozen by default — but in both editors (`Step2FieldValidation`, `KawasanGeometryEditor`) the lock is a **working state, not a verdict**: an explicit per-polygon toggle lifts it to correct a bad import and puts it back afterwards (and pins a hand-drawn polygon the same way). It is never toggled automatically, and only one polygon at a time. The flag persists for a pengajuan (it is part of `payload.polygons`); for a kawasan it lives only in the editor, since the saved row is the geometry alone.

**Nothing that draws kawasan is capped or paged**, and that is a decision, not an oversight: the overlap check runs in PostGIS over *every* kawasan, so a map showing a subset would render part of an answer already computed in full, and an officer cannot tell a kawasan that is absent from one that does not exist. Both map surfaces read `prohibitedAreas.geometriSemua` (unpaged, four columns, cached under the same `kawasan:` prefix `invalidateProhibitedAreas()` clears) rather than a page of `list`, and the editor's SPPTG layer reads `submissions.listMapPolygons` — already server-filtered to valid terdaftar/terdata, and carrying no applicant name, which suits a layer that only needs to show *that* a claim is there. A display cap was tried and removed; do not reintroduce one. Relatedly, `findCenter` (`src/lib/utils.ts`) must never go back to `Math.min(...values)`: spreading puts one argument on the stack per element, and flattening every kawasan into one array threw `Maximum call stack size exceeded` at around 100 000 points — `src/lib/find-center.test.ts` pins it at 200 000.

**Cek Tumpang Tindih** (`prohibitedAreas.checkOverlaps` → `findOverlappingSubmissions`, UI at Pengaturan → Kawasan → "Cek Tumpang Tindih", `/app/pengaturan/kawasan/tumpang-tindih`) is a **page**, not a dialog: it carries a map beside the table, and an officer follows a row into a pengajuan and comes back to it. The report counts only **`SPPTG terdaftar` / `SPPTG terdata` that are still `is_valid`**, against kawasan that are `aktif_di_validasi` — a rejected berkas inside a kawasan is the system working, not a conflict. The map is deliberately asymmetric: **every** kawasan is drawn (a kawasan with nothing in it is part of the answer to "where are the restricted areas"), but only the pengajuan that actually overlap one, since every other valid SPPTG would bury the handful that matter. It is gated to Superadmin/Admin/Verifikator because the geometry comes from `submissions.listMapPolygons`, a `verifikatorProcedure`.

Both this page and the dashboard carry a **crosshair button per table row that frames the map on that boundary** (`ReadOnlyMap`'s `focusGeoJSON` + `focusSignal` → `fitBounds`). Two things make it work. The signal is a **counter bumped per click**, because focusing is an action rather than a state — clicking the same row again after panning away has to bring the map back, and comparing the geometry cannot tell those clicks apart; the effect therefore depends on the signal alone, since the parent rebuilds the geometry object every render and including it would re-frame the map continuously. And the handler **scrolls the map into view**: the table sits below it, so framing a polygon the reader cannot see looks like nothing happened. The map's own polygon set is preferred over the clicked row's geometry — on the dashboard `submissions` is one page while `mapSubmissions` is every polygon in scope.

That page answers "who is standing in a kawasan we already have". The **Tambah/Edit Kawasan form asks the same question in the other direction, before the kawasan exists**: `prohibitedAreas.cekGeometriTumpangTindih` → `findKawasanGeometryConflicts` takes the boundary currently drawn and reports what it lands on — other kawasan *and* `SPPTG terdaftar`/`terdata` that are still valid, one query, split back apart by `summarizeKawasanConflicts` (`src/lib/kawasan-conflicts.ts`) because the two mean different things: a kawasan on kawasan is the office recording the same restricted land twice, while a pengajuan under it is somebody's registered claim about to be declared restricted. It is a **mutation purely for transport** — a kawasan traced from an SK runs to thousands of vertices and a query would put that geometry in the URL — and it passes the WKT as a **bound parameter**, unlike the `sql.raw` interpolation the create/update paths still use. Three rules. Unlike the report, it counts kawasan that are **not** `aktif_di_validasi` too (a duplicate of a switched-off kawasan is still a duplicate; the row carries the flag so the panel can say so), and it excludes the kawasan being edited — without that every edit reports a 100% clash with its own row. **Saving always runs the check**: `assertNoBlockingConflicts` refuses a `create`/`update` with a `CONFLICT` unless `abaikanTumpangTindih` is set, so the "tetap lanjutkan" tick box is a decision transmitted to the server, not a client-side formality a caller can skip by not asking. And the acknowledgement is bound to the geometry it was given for via `geometrySignature`: move a vertex and the result goes stale, the tick clears, and the check has to run again — an acknowledgement must never outlive the boundary it approved.

**Kawasan drafts** (`src/lib/kawasan-draft-storage.ts`, resumed via `?draft=<id>` on the tambah/edit pages and listed at the top of Pengaturan → Kawasan) exist because tracing a Kawasan Hutan out of an SK does not finish in one sitting. They live in **localStorage, not the database** — a draft asserts nothing about the land, so it never reaches Postgres and never enters the audit trail; the cost is stated outright in the UI, because a draft that silently only exists on one machine is the kind of thing an officer finds out the hard way. Three rules. The key is **per user** (`espptg:kawasan-drafts:<userId>`): a kabupaten office runs shared workstations, and without it the next person signing in is offered someone else's half-traced boundary as their own. A **quota failure is surfaced, never swallowed** — an SK boundary is thousands of vertices against a few megabytes of storage, so the write really can fail, and a "Simpan Draft" that silently did nothing is worse than an error. And a draft carrying `editingAreaId` resumes on **that kawasan's edit page**, since resuming it as a new kawasan would file the same boundary twice. Reads happen after mount (there is no `window` while the page prerenders), and the draft is deleted only in the mutation's `onSuccess` — dropping it on the attempt would throw the work away whenever the server refused.

**Kawasan geometry has ceilings** (`src/lib/kawasan-limits.ts`): `MAX_KAWASAN_BLOCKS` (500) and `MAX_KAWASAN_TOTAL_POINTS` (100 000). This does *not* walk back the rule above that a kawasan has no per-polygon cap — the parser is still handed `UNLIMITED_POLYGON_POINTS`, and the ceilings are ~1 000× the wizard's per-bidang limit, so a genuinely detailed single kawasan never meets them. They exist because a real file made the difference concrete: `SK_397_TAHUN_2025_KH_KALTIM.shp` (the Kawasan Hutan of the whole province) is 188 features holding **1 440 rings and 1.33 million vertices, 51 MB of GeoJSON**. That is not one kawasan, it is 188 of them, and the form writes one row — so it is **refused with a message pointing at QGIS, never truncated**, because a kawasan silently missing most of its blocks would then be enforced against real pengajuan. `src/lib/shp-zip-huge.e2e.test.ts` pins this against the actual file (skipped unless `KAWASAN_SHP_FIXTURE` points at it). Two matching performance rules in the editor, both of which that file broke: the coordinate table **pages** at `KAWASAN_COORDINATE_PAGE_SIZE` (a 249 210-point block is three quarters of a million DOM nodes, which hangs the tab rather than rendering) and its pager sits **outside** the `fieldset disabled` so a locked imported block stays browsable; and the UTM view converts only the visible page. **The maps are deliberately uncapped** — see below. For the same reason the overlap check's staleness is tracked with a **version counter**, not a hash of the geometry — `JSON.stringify` on a 50 MB boundary every render is work proportional to the parcel for a question that is only "did it change".

Two more rules in that form. **"Informasi Kawasan" only renders once a Blok Kawasan exists** — the attributes describe a boundary, and asking for them first puts the form in the wrong order; one block is always selected by then, since the editor activates the first automatically. And **submit validates every block**, via `findUnusableKawasanBlocks`: `polygonsToMultiPolygon` silently skips a block under three vertices, so without it a kawasan with a half-drawn block saved as a *smaller* kawasan than the one on screen.

**Impor Massal Kawasan** (`/app/pengaturan/kawasan/impor` → `KawasanBulkImport` → `src/lib/kawasan-bulk-import.ts` → `prohibitedAreas.createBulk`) is the other half of that refusal: the single form will not take a file of 188 kawasan, so this one splits it into 188 rows. **The file's own name column is what says where one kawasan ends** — `groupPolygonsIntoKawasan` groups on it, and two rings named `TN Kutai` are two blocks of one kawasan while `HP S. Santan` is a different one. Four rules. It groups on **`ParsedPolygon.featureName`, never `name`**: `name` carries per-ring numbering (`TN Kutai (1)`) so a polygon list does not repeat itself, and grouping on that filed each block as its own kawasan — 660 rows where there are 187. The parser's `NAME_FIELDS` now extends `KAWASAN_NAME_FIELDS` from `shapefile-attributes.ts` for the same reason: `NM_KWS` was in one list and not the other, so every feature came back unnamed and the whole province collapsed into one group. **Every kawasan is filled in on its own** (`KawasanRowAttributes`, one per group): the batch could have owned jenis/sumber/dasar hukum/tanggal — a boundary file does come from one SK — but *one SK is not one kawasan*, since a release routinely mixes Hutan Lindung with Hutan Produksi and Cagar Alam, and batch-only fields left an officer either importing three times or recording the wrong jenis on two thirds of the rows. So the table of kawasan **is** the form and what a row shows is what gets saved; "Isi Cepat" is a tool that *writes into* the ticked rows (`applyQuickFill`, only the fields actually filled, so setting one tanggal for all does not flatten a jenis set individually) rather than a layer resolved underneath them at save time. `createBulk` still accepts batch-level values as optional per-area overrides' fallback, but the client always sends every field per area. Completeness is therefore checked **per row** (`findRowsMissingAttributes`), and the nama is never seeded from a shared field — naming every row of a bulk import identically is the exact mistake this feature exists to avoid, so an unnamed group starts blank and reads as incomplete rather than as a kawasan called "(Tanpa nama)". **Nothing imports without being previewed** — a provincial SK covers kabupaten this office has no business recording — so every group is listed with its counts and ticked individually; oversized groups and names already on record (`prohibitedAreas.namaTerpakai`) are listed too but start unticked with the reason beside them. The upload is **batched by vertex count, not row count** (`planKawasanImportBatches`, `BULK_IMPORT_POINT_BUDGET`), because 1.33 M vertices is 51 MB of JSON and one kawasan of 40 000 points costs what forty of 1 000 do; each batch is one transaction, a failure stops rather than pressing on, and what already landed is un-ticked so a retry cannot re-file it. And **`createBulk` runs no overlap check, deliberately** — an SK is authoritative reference data whose areas legitimately touch each other, and checking per kawasan would be a hundred PostGIS queries over a million vertices; run "Cek Tumpang Tindih" afterwards instead. Its geometry is a **MultiPolygon per row** (Polygon-only would have meant one row per ring) and its WKT goes in as a **bound parameter**, since these boundaries come straight off an uploaded file.

**The importer is reachable from Tambah Kawasan, not only from its own page**, because that is where an officer with a boundary file actually goes. `KawasanGeometryEditor` groups every import and, when the file carries **more than one kawasan name**, holds it as `pendingImport` and asks instead of guessing: "buat N kawasan terpisah" hands the already-parsed groups to `<KawasanBulkImport handoff>` — which the tambah page renders in place, so nothing is uploaded or parsed twice — or "gabung jadi 1 kawasan" loads them as blocks of the one being drawn. Both readings are legitimate (a kawasan really can be several blocks) and only the officer knows which, so **neither is chosen automatically**; the merge option is disabled, with the reason shown, when the file is past the single-kawasan ceilings. The escalation is opt-in per caller: `onBulkImportRequested` is passed only by tambah, so the edit page — which is about one existing row — keeps loading a multi-kawasan file as blocks. A `.zip` is also read **once** now (`parseGeospatialFile` hands the same `ArrayBuffer` to `zipContainsShapefile` and `parseShapefileZip`); it used to be read twice, which on a 16 MB file meant two copies and two archive loads on the browser's main thread before a single coordinate existed.

**Shapefile attributes prefill the form** (`src/lib/shapefile-attributes.ts` → `ParseResult.atribut` → `onAttributesDetected`). The `.dbf` beside the geometry usually already holds the SK number, its date and the kawasan's name (`SK_PNJK`, `TGL_PNJK`, `NM_KWS` in the KLHK releases), so making an officer retype them off the file they just uploaded is asking for a typo. **One rule decides it: a field is suggested only when the file agrees with itself** — every feature must carry the same value. `NM_KWS` differing across 187 features means the file describes 187 kawasan, and filling the form from row 1 would put a confident, specific, wrong name on a boundary; the layer's file name stands in for the nama instead, and nothing else is guessed. A jenis is taken only when it matches `PROHIBITED_AREA_TYPES` (a fungsi code like `F_2025 = 100700` matches nothing and is left alone — the wrong jenis changes what the kawasan blocks). The form applies a suggestion **only to fields still empty** and names what it filled in a toast.

**File storage**: uploads go client → base64 → `documents.uploadFile` → S3 (`src/server/s3/s3.ts`), keyed `submissions/{category}/{timestamp}-{randomId}-{filename}`. Official form templates live at `template-documents/{filename}`, fetched via `documents.getTemplateUrl` (signed URL) or `documents.fetchTemplatePDF` (base64).

**PDF generation**: SPPTG certificates are rendered with react-pdf components in `src/components/pdf/`, with data mapping in `src/lib/spptg-pdf-data.ts` and `src/lib/pdf-generator.ts`. The footer cannot count pages for itself (a `Font.registerHyphenationCallback` interaction — see `DocumentFooter`), so **the page count must be knowable before anything renders**: `pagination.ts` owns the layout, including chunking everything that scales with the data into sheets: the saksi (four on the signature page, the rest on continuation sheets — **there is no cap on how many saksi a pengajuan may have**) and the coordinate attachment (lat/lon then UTM for the same rows, one sheet per bidang). Never let a page overflow instead of adding a sheet there — the footer will keep insisting on the wrong total. Page numbers are derived from the *data* alone, never from `PDFGenerationConfig`, so a config flag may hide a block but must not remove a page. Nomor persil and the tape measurements are per bidang, and **page 1 states them outright** — one row each for a single bidang; for two, the label and its colon print **once** and the values stack in the value column, each tagged with the bidang it belongs to (`12/A (bidang 1)` / `13/B (bidang 2)` — `MultiValueRow`). Repeating the label down the page would read as two different fields rather than one field with a figure per parcel. That is only safe because `MAX_POLYGONS_PER_SUBMISSION` is 2: the worst case is four extra rows on top of all eight boundary rows, which is exactly what `SPPTGDocument.test.ts` renders and asserts still fits one sheet. **It fits with nothing to spare** — a per-bidang *luas* row was tried and pushed page 1 onto a second sheet, so only the two totals (luas pengukuran, luas perhitungan peta) are printed. Raise the bidang cap or add a row here and that test is what will tell you. The stated total is summed per bidang — each contributes its own luas manual, or its drawn area when it was never measured by hand — so the figure on page 1 can never be one parcel's standing in for the lot.

**Two certificates** — Step 4 issues a different document depending on the Step 3 decision, and the difference is the point, not a cosmetic variant:

| | `SPPTG terdaftar` | `SPPTG terdata` |
|---|---|---|
| Nomor prefix | `TERDAFTAR/SPPTG/` | `TERDATA/SPPTG/` (`src/lib/nomor-spptg.ts`; the prefix is a fixed label beside the input, never part of its value, and `hasNomorSPPTGBody` is what "filled in" means) |
| Kepala Desa endorsement | printed | **dropped** — no desa signs off on contested land |
| Disclosure notice | none | yellow `TerdataNotice` block: a 13-row checklist of jenis kawasan, ticked from `overlapResults`, signed by the juru ukur |
| Softcopy | uploaded by hand | **generated and attached automatically**; the issue button only appears once it exists |
| Overlap rule | *any* overlap shuts Step 4 | only a clash with **another pengajuan** blocks; kawasan overlaps are disclosed on the notice instead |

The split lives in `src/lib/spptg-terdata.ts` (`blockingSubmissionOverlaps`, `checkedTerdataStatuses`) and is selected by `data.variant` inside the PDF. Two things that look tempting and are wrong: `deriveSubmissionStatus` must **not** promote an issued terdata berkas to `terdaftar` (the status would contradict the paper it just produced), and the terdata certificate stays in the `SPPG` document category so oversight roles keep seeing it — a separate category would be a second grant to forget.

## Gotchas

- Legacy mixed-case column: the submissions village column is `submissions."villageId"` — raw SQL and index definitions must quote it exactly.
- Drizzle configs exclude PostGIS system tables via `tablesFilter: ['!geography_columns', '!geometry_columns']` and `extensionsFilters: ["postgis"]` — keep these when editing the configs.
- Status enum values use the `SPPTG` prefix (`'SPPTG terdata'`, `'Terbit SPPTG'`, …); some older UI code uses a wrong `SKT` prefix (see Known Issues in AGENTS.md).
- If new authz columns are missing from a database, authenticated pages fail with HTTP 500 on `auth.me` / `drafts.getById`.
